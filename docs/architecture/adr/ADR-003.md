# ADR-003: Database migration tool selection

* **Status:** Approved
* **Date:** 2026-11-27
* **Authors:** Pair D
* **Depends on:** DEC-11, MA-23

## Context
GoJudge uses PostgreSQL as its primary relational data store, with database access and schema modeling planned in `INF-05` around `pgx` (driver/connection pool) and `sqlc` (type-safe Go code generation from SQL). Currently, the repository contains no database migrations or migration tooling. A standardized migration tool is required so that schema changes derived from `CON-05` are reproducible, version-controlled, and compatible with both `sqlc` schema inspection and `pgx`-based services or standalone migration jobs.

## Decision Driver & Approval Condition
- This decision depends on **DEC-11** and provides input to **INF-05** (alongside data contract **CON-05**).
- Tooling must integrate cleanly with **PostgreSQL**, **`pgx` (`pgx/v5`)**, and **`sqlc`** without maintaining duplicate schema definitions.
- Database migrations in GoJudge are serialized with a single owner per sprint, favoring predictable linear or timestamped SQL migration files.
- Mentor approval (MA-23) on 2026-11-27 selected `pressly/goose`. The alternatives and trade-offs below remain part of the decision record.

## Considered Options

### Option 1: `pressly/goose`
* **Compatibility with `pgx` and `sqlc`:** Uses plain `.sql` migration files annotated with `-- +goose Up` and `-- +goose Down` directives. `sqlc` natively parses `goose` SQL files directly as its DDL schema source without requiring a running PostgreSQL instance during code generation. Connects to PostgreSQL via `pgx/v5/stdlib` (`database/sql` adapter).
* **Trade-offs:**
  * *Pros:* Direct compatibility with `sqlc` schema parsing; supports both standalone CLI execution (e.g., Kubernetes Job / local dev) and programmatic execution embedded in Go binaries via `embed.FS`; supports Go-based migrations alongside SQL migrations if complex data backfills are ever required; supports both sequential and timestamped versioning.
  * *Cons:* Requires tool-specific `-- +goose Up/Down` SQL comments inside `.sql` files; uses the `database/sql` interface over `pgx/v5/stdlib` rather than a native `pgx` interface.

### Option 2: `golang-migrate/migrate`
* **Compatibility with `pgx` and `sqlc`:** Uses paired plain SQL files (`<version>_<name>.up.sql` and `.down.sql`). `sqlc` natively reads `.up.sql` files as its schema source. Provides a dedicated `pgx/v5` database driver (`database/pgx/v5`) as well as a standalone CLI and official container image.
* **Trade-offs:**
  * *Pros:* Mature, widely adopted in Go projects; clean `.up.sql` / `.down.sql` files without special comment annotations; native `pgx/v5` driver support without `database/sql` wrapper overhead; straightforward execution as a separate Kubernetes InitContainer or Job.
  * *Cons:* Supports SQL migrations only (no Go-code migrations); strict sequential integer prefixes (`000001`, `000002`) can conflict if parallel branches ever draft migrations simultaneously.

### Option 3: `ariga/atlas`
* **Compatibility with `pgx` and `sqlc`:** Supports versioned SQL migration directories compatible with `sqlc` and connects to PostgreSQL via standard `postgres://` connection URLs alongside `pgx`-based applications.
* **Trade-offs:**
  * *Pros:* Built-in schema diffing, migration linting, and drift detection.
  * *Cons:* Introduces a heavier external CLI binary/toolchain dependency, splits features between open-source and commercial licenses, and adds operational complexity beyond what is needed for serialized migrations in this project.

## Decision
**Approved choice:** **`pressly/goose`** is the database migration tool for GoJudge, as selected by the mentor under DEC-11 / MA-23 on 2026-11-27.

**Justification:**
1. **`sqlc` native synergy:** `goose` `.sql` migration files serve as the single source of truth for both database schema evolution and `sqlc` code generation, eliminating schema duplication.
2. **`pgx` & deployment flexibility:** Works seamlessly with `pgx/v5/stdlib` and offers both a lightweight CLI (for local development and CI/Kubernetes migration jobs) and an embeddable Go library (`embed.FS`).
3. **Extensibility:** Supports standard SQL migrations for DDL changes while retaining the option to write Go migrations if complex data transformations arise in later sprints.

## Consequences
* **Single schema source of truth:** Once `INF-05` begins after agreement on the applicable CON-05 slice, DDL files managed by the chosen migration tool will directly drive `sqlc` model and query generation.
* **Operational consistency:** All developers and deployment pipelines will apply and roll back schema changes using a single versioned workflow.
* **Implementation gate:** INF-05 must use this approved tool. Contract agreement and the SDD gates for the applicable CON-05 slice remain independently required.
